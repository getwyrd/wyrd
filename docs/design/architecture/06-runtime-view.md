# 6. Runtime view

> Living document. The scenarios that most define the system's behavior. See `diagrams/` for sequence diagrams.

## 6.1 Write path (the commit point)

The headline scenario; see `diagrams/write-path-sequence.mermaid`. Detailed step-by-step in section 5 (L4 write protocol) and normatively in the commit-protocol spec.

**Step 0 — resolve the home zone (L2).** Before any data moves, the access layer resolves the target against the global namespace (`NamespaceStore`, ADR-0020): an existing object returns its **home zone** (cached after first use); a new object is assigned a home zone and replica set by the **placement service** from policy — residency, replication factor, capacity. Steps 1–4 then run entirely *within that home zone*.

**Steps 1–4 — stage and commit (home zone).** As detailed in section 5: the client registers chunk IDs in the pending ledger, erasure-codes and writes fragments directly to the home zone's D servers — bulk data crosses no shared component, the basis of the throughput-scaling claim — then issues the single atomic metadata mutation that *is* the commit point. The file does not exist until that mutation and fully exists after it.

**Two linearization points, not one.** Introducing or moving a *name* (create, rename) is linearized globally by L2, so it is visible in every zone and never lost or resurrected (section 8.1); a file's *content version* is linearized at its home zone by the commit point. For a new object the global name is published only once its first content version has committed, so no reader anywhere sees a name without content. The exact interleaving is owned by the commit-protocol spec.

**Publishing a map that does not fit one value.** A segmented chunk map (section 6.2, step 2) cannot be written in a single mutation, so it is published in two staged phases: the segment records are committed first, in **budgeted** batches — each batch, and each record inside it, sized against the tightest backend's transaction *and* per-value limits, since a record over the value ceiling is rejected permanently rather than retryably, and bounded in **operations** as well as bytes, since a transaction of many tiny mutations is inside every size limit while still spending the backend's per-transaction deadline on sequential round trips — and only then is the inode root **flipped** to name the new generation. The flip is one batch that also carries the publisher's own mutations, so the publication instant and the publisher's state change land together or not at all. Both phases run under the **publisher's fence** — one declared record, pinned by every batch of both phases, since a batch pinned to some *other* record is overtaken by the rollback exactly as an unfenced one is: the rollback that reclaims a crashed attempt deletes that attempt's segment records, and the fence is what makes a stale publisher lose to it rather than flip a root over records that are already gone. The flip must also **move** that record, not merely pin it, or the racing rollback's own precondition still holds *after* the publication and it deletes the segments the now-live root names — and it must not move it **back** to a state the publication has already left, since a fence that returns to a value it held re-arms every precondition that was satisfiable there, which is the same deletion one step later; the rule therefore spans the segment phase and the flip together rather than each phase alone. And a publication refuses to flip over a segment range it cannot fully account for: a record left behind by a longer earlier attempt at the same generation, or a key in that range no resolve could read, is a refusal before the first write, and so is a range that does not yet hold **every** segment the root would name — publishing over any of them would report success and leave an object no consumer could ever resolve, with no prior generation left to fall back to and no crashed attempt for a rollback to find. Until the flip commits, readers and custodians see only the prior generation; a crashed attempt leaves segment records that its own epoch scopes and its rollback reclaims.

## 6.2 Read path

See `diagrams/read-path-sequence.mermaid`.

1. **Resolve the home zone (L2).** Resolve the path/key against the global namespace → file identity, **home zone**, and an ACL check (cached after first use). Consistency-sensitive reads route to the home zone (section 6.6); stale-tolerant reads may target a nearer replica.
2. **Fetch the chunk map (L4).** From the home zone's metadata store — or a version-fenced replica — get the chunk list, fragment locations, and EC scheme (cached after first read). In steady state both metadata hops are cached, so a hot read goes straight to the data path.
   A chunk map is **one metadata value**, and a value has a ceiling (100 KB on the tightest backend in play), so a large object's map is **segmented**: the inode root carries a segment-group identity (`{nonce, epoch}`) plus a segment table, and each segment's chunks live in their own `seg:<nonce>:<epoch>:<index>` record. Resolving it is the root plus **one bounded range read** of that group's segments, ordered by the segment index the resolver parses out — never a whole-namespace scan, and never a budget the root sets for itself: a table naming more segments than the object ceiling allows is refused for that object, unread, rather than performed — the record still decodes, because a capacity ceiling that moved must not make already-published objects unreadable, but no consumer will spend the read it claims. **Every** consumer of a chunk map resolves it through the same call: the read path, GC's reference build, scrub, reconstruction, rebalance, backfill and post-restore reconciliation, so no representation of an object's bytes can be understood by one process and opaque to another. A segment that is absent — or unreadable, or holding a byte span the root's table does not name — while the root still names its generation is a **fail-closed error**, never a partial map; the same anomaly under a root that has moved on (a concurrent supersede or delete) means that *generation* was retired, its records are being deleted, and the resolve **restarts against the current root** — for a reader that is the new generation's bytes rather than a spurious "no such key", and for a maintenance pass it is the live generation's fragments rather than an empty answer that would drop a live object out of the protected set. A maintenance pass resolves against the **live root** in any case, not against the record its own scan decoded: a scan is a snapshot, minutes old at the far end of a large store, and protection computed over a generation the object no longer has is the same failure by another route. Only a root that is genuinely gone (or not committed) resolves to nothing, and a resolve that keeps meeting a retired generation fails closed rather than answering that the object owns no bytes. Fail-closed is **scoped to the object that failed**: a read of an unresolvable object is an error for that key alone, every other object in the store still reads, and no pass that can reclaim bytes acts on an incomplete reference set. Nor does a pass that *verifies* certify one: the proactive bit-rot scrub reads the same reference set, so an object missing from it is an object whose fragments were never fetched or checksummed — the pass verifies every other object as usual, names the one it could not, and reports the store as **not certified** rather than as clean. The scoping holds for the passes that *walk* every object as much as for the read of one: a record a pass cannot read is attributed on the audit seam and skipped, and the walk continues over the rest of the store — the pre-M3 placement drain still drains, a decommission still evacuates the servers the damaged object has nothing to do with, and a queued repair for a healthy chunk is still assessed rather than starved behind the damaged record. Nothing of the unreadable object is filled, moved or reclaimed on the way past it, and a repair obligation whose chunk may live in it is **kept queued** rather than retired as referenced by nothing — the containment is a narrower blast radius, never a weaker rule. It is narrower again for a record that was never **committed**: every one of these passes acts on committed objects only, so an unreadable record whose remaining bytes still say plainly that it is uncommitted was in no pass's population to begin with — it is attributed like any other damage and holds nothing back, because a record that authorizes nothing must not be able to stop reclamation, evacuation, repair or a clean post-restore report. The doubt runs one way only: a record whose state cannot be read at all is treated as possibly committed, since mistaking a committed object for an uncommitted one would drop its bytes out of the protected set — the one failure this whole containment exists to prevent. A surface that only *reports* — the drain/decommission status an operator reads per D server — neither certifies nor fails: it answers that the drain is blocked and **names the object to repair**, because refusing to answer at all would take the whole fleet's drain status down for one damaged object, and certifying would invite an operator to decommission a server whose bytes a live object may still own. Startup recovery is deliberately outside that population — it derives the id-allocator floor from the segment records themselves rather than by resolving any root, so one damaged object can never stop a gateway from serving all the healthy ones. That floor is **total**: no arrangement of stored records can make it refuse, and a record it cannot decode costs it only the typed reading — the record is attributed in the audit log and its chunk ids are still recovered from its bytes, because a floor that quietly skipped them would let the allocator re-mint an id whose fragments are still on disk. Recovering them covers the case where the damage took the ids *with* it: a value of a record class whose whole content is a chunk list, naming no chunk id at all, has lost the ids it was holding rather than legitimately holding none, and contributes the top of the in-process id range instead of nothing — while a *root* naming no chunk id is an ordinary root (an empty object, or a segmented one whose ids live in its segment records) and contributes what it names, so one damaged root can never park the allocator. Totality is why it reads every namespace it needs in **bounded pages** rather than whole-namespace scans, which are complete-or-fail-loud above a cap: a store merely too large to scan would otherwise stop the gateway from starting just as effectively as a corrupt record would.
3. **Read fragments directly from D servers.** Holding the EC logic, the client needs only *k* of *n* fragments and reconstructs from whichever *k* arrive first — turning erasure coding into a tail-latency *advantage*: a slow or dead disk does not slow the read.
4. **Verify checksums** on every fragment, catching bit rot at read time; re-read elsewhere on failure.

## 6.3 Repair (self-healing, intra-zone)

Driven by custodians (L4):

1. **Scrub** — continuously read fragments, verify checksums against metadata, detect bit rot *before* the data is needed.
2. **Reconstruct** — on D-server loss or failed checksum, read any *k* surviving fragments, recompute the missing ones, place them on healthy servers in correct failure domains, and update the chunk's location via a single atomic metadata mutation — the same commit-point pattern as a write.
3. **Rebalance** — proactively move data off draining/hot servers, preserving failure-domain invariants.

Every recovery action is itself commit-point-atomic. A crashed repair job leaves garbage (collected later), never corruption.

The metric that matters: **time-to-repair vs. failure rate**. Durability ("the nines") is essentially the probability that more than *m* fragments fail within one repair window. Fast, parallel repair matters more than wide encoding. This is why repair-queue depth and time-to-repair are first-class telemetry (ADR-0011), not vanity metrics.

**Repair vs. serve.** A D-server loss makes both clients (read reconstruction, section 6.2) and custodians (repair reconstruction) read the surviving fragments, so they contend. Repair reads are throttled **below** foreground reads to protect read latency — but repair priority **rises as redundancy falls**, so a chunk near its durability floor (close to losing its *m*-th fragment) preempts foreground work. Durability is gate-zero (goal 1); latency yields to it only when redundancy is genuinely threatened. This dynamic priority is part of the admission/backpressure model (section 8.9).

## 6.4 Cross-zone replication and zone-loss recovery

- **Replication** (L3): after a home-zone commit, replication workers copy chunks to other zones per policy. The remote replica becomes readable only when its record commits in L2 — never mid-copy.
- **Zone loss** (L3 global custodians): detect the dead zone, find every file now below its policy replica count, re-replicate from survivors. Effective geographic durability is bounded by cross-region bandwidth and rebuild parallelism — the same repair-time principle at planetary scale.

## 6.5 Disaster recovery ordering

After a real disaster, restore in dependency order:

0. **Trust plane (provider CA) first of all** — re-establish the CA (`step-ca` now, SPIRE reserved — ADR-0036) and distribute the trust bundle, because every step below dials over **fail-closed mTLS** (ADR-0005, ADR-0025) and cannot even complete a handshake without it. (In the single-binary profile the built-in dev-CA makes this a no-op; a real fleet must stand up the CA before anything else.)
1. **L5 coordination** next — so components can find each other and elect leaders.
2. **L2 / L4 metadata** — so the map to the bytes exists. Restored from out-of-band backups that do **not** depend on the system being restored.
3. **L3 replica verification and re-replication** — so the bytes are protected again.

Restoring bytes before the map is useless; restoring the map before coordination cannot even start; and coordination itself cannot complete a single mutually-authenticated dial before the trust plane exists. This ordering is a runbook section and must be written and drilled before it is needed.

## 6.6 Consistency at runtime

See section 8 (the consistency contract). In brief: the namespace is globally strongly consistent; a file's writes are linearizable at its home zone; per-session read-your-writes and monotonic reads are provided (v1: by routing consistency-sensitive reads to the home zone); stale-tolerant reads may be served from a lagging replica; cross-session visibility of a remote write is eventually consistent, bounded by replication lag.

## 6.7 Delete and space reclamation

Delete is a commit-point operation too, and its cost is paid lazily, off the critical path.

1. **Unlink (the commit point).** Removing the dirent — and tombstoning the inode/version — is a single atomic metadata mutation, linearized globally by L2 for the *name* so no zone ever resurrects a deleted file (section 8.1). The delete acknowledges here; the object is now invisible to every consistency-sensitive reader and its chunks are unreferenced.
2. **Reclaim (custodian GC, L4).** The orphaned fragments are reclaimed by a GC custodian after a grace period — long enough that an in-flight reader holding the old version is never torn — exactly the pending-ledger sweep pattern (section 5). Reclamation is background work, not on the delete's latency path.
3. **Propagate across zones (L3).** If the object had replicas, the deletion propagates through the replica catalog: each holding zone drops its catalog record and its GC reclaims the local fragments. Until propagation completes, a *stale-tolerant* read in a lagging zone may still see the old object, bounded by replication lag (section 8.1); consistency-sensitive reads route to the home zone and never do.
4. **Prove it (audit + crypto-erase).** The deletion is recorded in the append-only audit/event log — the operator's compliance and GDPR-deletion story (section 8.3). Where per-tenant envelope encryption is enabled, dropping the object/tenant key crypto-shreds the data immediately, making it unrecoverable independent of when GC runs (section 8.5).
