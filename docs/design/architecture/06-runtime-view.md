# 6. Runtime view

> Living document. The scenarios that most define the system's behavior. See `diagrams/` for sequence diagrams.

## 6.1 Write path (the commit point)

The headline scenario; see `diagrams/write-path-sequence.mermaid`. Detailed step-by-step in section 5 (L4 write protocol) and normatively in the commit-protocol spec.

**Step 0 — resolve the home zone (L2).** Before any data moves, the access layer resolves the target against the global namespace (`NamespaceStore`, ADR-0020): an existing object returns its **home zone** (cached after first use); a new object is assigned a home zone and replica set by the **placement service** from policy — residency, replication factor, capacity. Steps 1–4 then run entirely *within that home zone*.

**Steps 1–4 — stage and commit (home zone).** As detailed in section 5: the client registers chunk IDs in the pending ledger, erasure-codes and writes fragments directly to the home zone's D servers — bulk data crosses no shared component, the basis of the throughput-scaling claim — then issues the single atomic metadata mutation that *is* the commit point. The file does not exist until that mutation and fully exists after it.

**Two linearization points, not one.** Introducing or moving a *name* (create, rename) is linearized globally by L2, so it is visible in every zone and never lost or resurrected (section 8.1); a file's *content version* is linearized at its home zone by the commit point. For a new object the global name is published only once its first content version has committed, so no reader anywhere sees a name without content. The exact interleaving is owned by the commit-protocol spec.

## 6.2 Read path

See `diagrams/read-path-sequence.mermaid`.

1. **Resolve the home zone (L2).** Resolve the path/key against the global namespace → file identity, **home zone**, and an ACL check (cached after first use). Consistency-sensitive reads route to the home zone (section 6.6); stale-tolerant reads may target a nearer replica.
2. **Fetch the chunk map (L4).** From the home zone's metadata store — or a version-fenced replica — get the chunk list, fragment locations, and EC scheme (cached after first read). In steady state both metadata hops are cached, so a hot read goes straight to the data path. One metadata value has a size ceiling, so a large object's map is **segmented**: the root carries the group identity and a segment table, and the chunks live in that group's own records. Resolving one is the root plus **one bounded range read** of that group's records — scoped to that group *and* that epoch, never a global scan — assembled in **parsed-index** order. The work that read may cost is the reader's number, not the record's: a table naming more segments than the reader's ceiling allows is refused **unread**, and each page asks for a fixed number of rows the reader chooses. (How many *bytes* a value costs to receive is the metadata store's bound, not the reader's — the store seam inherits each backend's native value limit.) Resolution is **single-sourced**: one resolver turns a committed root into that ordered list, so every consumer that can resolve — the whole-object, streaming and ranged read paths, and the maintenance passes that build the protected reference set (section 6.3) — learns which chunks an object owns the same way, and a consumer that has not yet adopted it refuses a segmented map outright rather than answering from the root alone. Three arms close the race with retirement, told apart by what a single re-read of the root sees: a generation **superseded** mid-resolve drops the stale resolution and **restarts against the live root** — never a torn or empty answer; a root found **gone** is a deletion, answered as "no such object" where it is seen rather than retried, since no later generation exists to restart onto; and an anomaly on a generation the root **still names** (an absent, undecodable, or mismatched segment — or a root record one of those re-reads cannot parse at all) **fails closed** with a typed error, scoped to that one object. Every fault a resolve raises about an object's own bytes is typed that way, so a maintenance consumer can tell "this object is unreadable" (contain it, keep walking) from "the store is failing" (end the pass). Restarts are budgeted, and running out is a typed error about that object — never "it owns no bytes".

   A maintenance pass resolves **every** committed object this way to build the set of fragments it must protect, and one object it cannot read leaves that set **incomplete** — which every pass reading it must then say out loud, because reclamation-safety and certification-honesty are the same property read twice. No pass that can **reclaim** bytes acts on an incomplete reference set: it deletes nothing, fleet-wide, since an unreadable map hides *which* chunks its object owns and no fragment can be shown not to be one of them. A pass that only **verifies** does not certify one either — it verifies every other object, names the one it could not, and reports the store **not certified** rather than clean. The operator-run pass that reconciles the fragment tier after a **metadata restore** answers the same way: it still reports every object it could read — what it marked collectable, and which chunks are unreadable, misplaced or under-replicated — names the ones it could not, and refuses to call the run clean, because a report drawn over part of a store is not a clean bill for it, and one damaged record must not leave an operator with no report at all at the moment they most need one. Its marks and its report rest on **one** reading: a record either read of the committed namespace could not read withholds every mark in the fleet, and a fragment either read finds referenced is never marked — two readings that can disagree are two conclusions, and the operator is shown one of them. A **report-only** surface reading that set (a drain's reconciliation status) is held to the same rule and never answers "satisfied" over an incomplete one: telling an operator a server is safe to decommission is the reclamation decision in another form. That surface also **names the blocking record**, which is what distinguishes it from the ordinary "not yet" of a server still holding referenced fragments — one says an evacuation is running and will finish, the other that nothing will converge until a named record is repaired, and an operator who cannot tell them apart is left waiting on a stall with no way out. The containment is per object throughout — the damaged record is attributed and the walk continues, so one unreadable object costs the store one object's availability, not every healthy object's protection.
3. **Read fragments directly from D servers.** Holding the EC logic, the client needs only *k* of *n* fragments and reconstructs from whichever *k* arrive first — turning erasure coding into a tail-latency *advantage*: a slow or dead disk does not slow the read.
4. **Verify checksums** on every fragment, catching bit rot at read time; re-read elsewhere on failure.

## 6.3 Repair (self-healing, intra-zone)

Driven by custodians (L4):

1. **Scrub** — continuously read fragments, verify checksums against metadata, detect bit rot *before* the data is needed.
2. **Reconstruct** — on D-server loss or failed checksum, read any *k* surviving fragments, recompute the missing ones, place them on healthy servers in correct failure domains, and update the chunk's location via a single atomic metadata mutation — the same commit-point pattern as a write. That mutation rewrites whichever record holds the chunk's reference: the inode record of a flat map, or the one `seg:` record of a segmented map (section 6.2), whose root is pinned and never rewritten. It is a compare-and-swap on the root generation, and, for a segmented map, on the segment record as the move itself re-reads it, and on the chunk's own reference — so a concurrent move of a *sibling* chunk in the same segment record is merged, while a superseded generation or a chunk moved under the plan makes the repair lose and retry next pass — and it also drains the repair obligation and marks each displaced fragment an orphan, under a precondition on the mark it read at that position (one GC is already reclaiming, or one it cannot read, is left exactly as it is). Before it writes a rebuilt fragment, the repair marks the destination position — a pre-mark, carrying an identity fresh to this move, that replaces whatever mark the position held, never one GC is already reclaiming or one it cannot read, which it passes over for another position (the server may still take another of the chunk's fragments) or waits out — and sends the write only while that pre-mark is young, with a deadline the D server enforces; the same atomic mutation that repoints the chunk then clears the pre-mark, and holds only while the pre-mark is exactly as written, so a repair never publishes a placement over a position GC has begun to reclaim. A fragment rebuilt in place, on the server its placement already names, gets no pre-mark: that position never stops being named, so the repair instead clears whatever stale mark it holds, in the same guarded step that writes the other destinations' pre-marks, before any write. A mark therefore never outlives its event on a position a committed placement names — however the repair ends — and a repair that loses its race leaves what it wrote under its pre-mark, for GC to reclaim, or on a position the placement still names. One case is left open (#1100): any unreference whose mark is stamped before that guarded step (the in-place batch) and commits after it — a delete or a flat overwrite at the gateway, or a competing move of the same fragment — can leave the fragment rebuilt in place with neither a reference nor a mark, because GC may retire that early mark before the write lands; those bytes are kept, never lost. A repair refused on the way — no usable destination position, a pre-mark too old to write under, a write the D server refused at its deadline or could not certify, or a pre-mark or an adopting mutation that lost to a changed mark or segment record while the object's root generation still stood — keeps its obligation queued, is named by its reason, and the pass does not certify. A repair that loses to a root generation that moved — a supersede, or a sibling chunk's repoint in the same flat record — is named a conflict instead, and the pass does not certify over it either: a root that moved does not show this chunk was repaired, so its obligation stays queued for the next pass to read again. A repair with no free failure domain to place its rebuild is kept the same way and not certified over; it is counted on the repair-blocked level rather than named as a refusal. An object the move cannot rewrite (a segment record that is absent, undecodable or would cross the value ceiling, or a segmented root stored under a key that is not the canonical `inode:<id>` spelling) is named for the operator, nothing is written for it, its obligation stays queued, and the pass does not certify.
3. **Rebalance** — proactively move data off draining/hot servers, preserving failure-domain invariants. Each evacuation is the same committed move as a repair: it copies the fragment under the same destination pre-mark, write deadline and adopting mutation.

Every recovery action is itself commit-point-atomic. A crashed repair job leaves garbage (collected later), never corruption.

The metric that matters: **time-to-repair vs. failure rate**. Durability ("the nines") is essentially the probability that more than *m* fragments fail within one repair window. Fast, parallel repair matters more than wide encoding. This is why repair-queue depth and time-to-repair are first-class telemetry (ADR-0011), not vanity metrics.

**Repair vs. serve.** A D-server loss makes both clients (read reconstruction, section 6.2) and custodians (repair reconstruction) read the surviving fragments, so they contend. Repair reads are throttled **below** foreground reads to protect read latency — but repair priority **rises as redundancy falls**, so a chunk near its durability floor (close to losing its *m*-th fragment) preempts foreground work. Durability is gate-zero (goal 1); latency yields to it only when redundancy is genuinely threatened. This dynamic priority is part of the admission/backpressure model (section 8.9).

## 6.4 Cross-zone replication and zone-loss recovery

- **Replication** (L3): after a home-zone commit, replication workers copy chunks to other zones per policy. The remote replica becomes readable only when its record commits in L2 — never mid-copy.
- **Zone loss** (L3 global custodians): detect the dead zone, find every file now below its policy replica count, re-replicate from survivors. Effective geographic durability is bounded by cross-region bandwidth and rebuild parallelism — the same repair-time principle at planetary scale.

## 6.5 Disaster recovery ordering

After a real disaster, restore in dependency order:

0. **Trust plane (provider CA) first of all** — re-establish the CA (`step-ca` now, SPIRE reserved — ADR-0036) and distribute the trust bundle, because every step below dials over **fail-closed mTLS** (ADR-0005, ADR-0025) and cannot even complete a handshake without it. (In the single-binary profile the built-in dev-CA makes this a no-op; a real fleet must stand up the CA before anything else.)
1. **L5 coordination** next — so components can find each other and elect leaders.
2. **L2 / L4 metadata** — so the map to the bytes exists. Restored from out-of-band backups that do **not** depend on the system being restored.
3. **L3 replica verification and re-replication** — so the bytes are protected again.

Restoring bytes before the map is useless; restoring the map before coordination cannot even start; and coordination itself cannot complete a single mutually-authenticated dial before the trust plane exists. This ordering is a runbook section and must be written and drilled before it is needed.

A metadata restore also brings multipart uploads back: an upload torn down after the restore point returns open while its staged bytes may already be reclaimed, and a retried Complete would publish over them (proposal 0016, D-B). So the post-restore reconciliation, run with writers stopped and before any gateway serves multipart requests, fences every open upload, and every one caught mid-Complete, last, after every chunk verdict is drawn: one metadata commit per upload moves the session to aborting and installs the retirement obligation owing all its staged records and parts, and it lands only if the session is still exactly as read and no obligation already holds a key it installs. One caught mid-Complete also gets a second obligation, the only deleter of the segment records its attempt wrote (0016 X57); its parts are owed as "all", since none can join once a Complete starts and a sparse list may not fit one metadata value. An upload the fence cannot settle — its record will not decode, it is at its last epoch, it changed mid-pass, or an obligation key is taken — is left as it was and named for an operator, and the command exits non-zero. Every run also names for an operator a fenced attempt whose segment records include one naming a chunk no part holds, not decoding or under a stray key, or whose second obligation will not decode, owes anything but that range, or is missing while such records remain: a drain deletes those records without marking any bytes, or nothing ever does. If a fence commit fails, the summary of every verdict is still written to the audit trail, marked incomplete and never clean, before the error; a re-run finishes the work and fences nothing twice.

Each run of that pass also records its progress as the restore-fence generation (section 5's `mpufence` record). Before its first write it records a new generation, not complete; after its last, it records that generation complete only if every write it made landed and no upload is left for an operator. Every run re-reads each fenced upload's records instead of trusting an earlier run's verdict, so neither a run that was cut short nor one over residue nobody repaired completes the generation. A restore rewinds this record too: an image taken after an earlier run completed reads complete until the next run starts. So until gateways check the record beside a restore-scoped signal (#508), multipart is kept safe by order alone: the pass runs before any gateway is re-enabled.

## 6.6 Consistency at runtime

See section 8 (the consistency contract). In brief: the namespace is globally strongly consistent; a file's writes are linearizable at its home zone; per-session read-your-writes and monotonic reads are provided (v1: by routing consistency-sensitive reads to the home zone); stale-tolerant reads may be served from a lagging replica; cross-session visibility of a remote write is eventually consistent, bounded by replication lag.

## 6.7 Delete and space reclamation

Delete is a commit-point operation too, and its cost is paid lazily, off the critical path.

1. **Unlink (the commit point).** Removing the dirent — and tombstoning the inode/version — is a single atomic metadata mutation, linearized globally by L2 for the *name* so no zone ever resurrects a deleted file (section 8.1). The delete acknowledges here; the object is now invisible to every consistency-sensitive reader and its chunks are unreferenced.
2. **Reclaim (custodian GC, L4).** The orphaned fragments are reclaimed by a GC custodian after a grace period — long enough that an in-flight reader holding the old version is never torn — exactly the pending-ledger sweep pattern (section 5). Reclamation is background work, not on the delete's latency path.

   The ledger of these grace records can outgrow what one metadata listing may return — a single delete of the largest segmented object writes more records than that — so GC **walks it in bounded windows** rather than reading it whole. Each pass reads at most a fixed number of records, in pages, starting where the previous pass stopped, and returns to the start of the ledger once it reaches the end; where to resume is kept in one small record of its own in the metadata store, so the walk carries over from pass to pass and across a change of leader. A pass that stops short of the ledger's end reports the walk as partial rather than the store as converged, so a caller that drives reconciliation until it is satisfied keeps going; and a resume record that no longer spells a key the ledger could hold (torn, oversized, damaged) is named to the operator and the walk restarts from the head, rewriting the record, rather than failing every pass on it. A pass concludes only what its window shows: a fragment whose record lies outside the window is left for a later pass, never reclaimed meanwhile on other evidence such as an expired write lease; a record whose value cannot be read still counts as a record — its fragment is kept and the record is named to the operator — and only a record spelled exactly as the delete path writes it can license a reclaim. The chunk-wide lease entry of an interrupted write is retired only once no fragment it accounts for is left, since other windows may still hold some. GC's own clean-up writes go out in commits of a fixed size, never one commit sized by the pass. The post-restore pass reads the same ledger page by page too, to its end, before deciding which fragments already carry a record.

   Reclaiming a **marked** fragment is recorded before its bytes are destroyed. GC first moves the fragment's record to a terminal *reclaiming* state — a compare-and-swap against the exact value it read, many records to one commit of the same fixed size — and deletes the fragment, and after it the record, only once that commit has landed. A mover that pre-marked a position and later adopts it preconditions its adoption on the record's earlier value, so from the instant the reclamation is recorded the adoption fails, instead of landing between the fragment's deletion and the record's and publishing a placement over bytes that are gone. A record that changed after GC read it loses its swap and keeps its fragment without costing any other record in the commit anything, and a pass that lost one and reclaimed nothing does not report the store converged. A record left *reclaiming* over a fragment still on disk — a pass that stopped between the swap and its deletes — is finished by the next pass with no second grace wait; one left over bytes already deleted is safe, since nothing can adopt it, and though a walk driven by the fragments on disk never revisits it, the sweep of records with no fragment beneath them, below, removes it. A fault that ends a pass after it has deleted fragments still commits their record deletes first, as far as it can. The bytes of an interrupted write carry no record and are reclaimed on their expired lease as before. A multipart retirement that is still draining never has its fragments reclaimed: its drain is what marks them, each record naming the retirement, and GC looks that retirement up by key — one read per fragment it would reclaim, never a listing of the retirement namespace — so a fragment it marked is reclaimed only once the retirement has finished draining and the record's own grace has run.

   GC also removes **records with no fragment beneath them**. A walk driven by the fragments on disk never reaches such a record — the old position of a repaired missing fragment, a record left *reclaiming* after its fragment was deleted, and later the planned positions a failed upload marks or a move marks before it writes — so without a sweep of its own it would stay in the ledger for good. A pass deletes a record of its window whose position none of that pass's own listings reported, once the record is older than the **late-write deadline**: the longest a mover may take between marking a position and authorizing the write into it, plus the longest an authorized write may take to land, plus the most two hosts' clocks may disagree. That rule is applied only to records written **after** their fragment — the plain grace record a delete or a vacated source leaves, and GC's own *reclaiming* record: a record that names the event which wrote it may have been written ahead of its fragment, and a write whose effect the store could not verify in time may still land beneath it, so such a record is left for the pass that owns its writer. The one exception is a grace record the retirement drain wrote (below): it is kept while the obligation it names is present, one keyed read of that obligation, and swept like a plain grace record once the obligation is gone, since the drain marks a position only after every write into it was authorized and nothing else would ever delete it; a write that straddles its deadline by longer than the gap left between those two instants and lands after the sweep leaves a fragment with no record, which GC keeps rather than reclaims. The sweep's deletes, like GC's reclaim intents, go out in commits bounded by the transaction's operation budget rather than its byte budget, and a commit whose result the store could not report is judged as the one all-or-nothing commit it was, from a read of every record in it, once the store says it is out of flight: a record still holding what the pass read shows the commit did not land, so a record gone was another writer's delete; with no such survivor a record gone is recorded as gone but claimed as nobody's delete, since the pass cannot tell its own from another writer's; and a commit that may still land is named to the operator and left to the next pass. Every writer that marks a position before its fragment lands must hold to the first two, and the deadline sits strictly inside the grace window, which the build checks. The pass's clock is read before any of its listings is taken, so a listing that shows the position empty past that deadline shows it will stay empty; a listing an earlier pass took never counts, and a record on a server the pass did not list is left alone. The sweep answers to the reclaim's own protections — a record at a position a committed object or a staged upload names is kept, and while the set of committed objects is incomplete nothing is swept — and a record whose value cannot be read is kept, as is any key not spelled exactly as the delete path writes it. Each delete is conditioned on the exact value GC read, in commits of the same fixed size, so a record rewritten in the meantime survives; a delete that loses is judged again on a fresh read of the record, never on the lost condition alone; and each delete is audited and counted only after its commit has landed.

   Bytes a multipart upload has staged but not yet published — the fragments its committed parts and its in-flight staging entries name — are protected as a class of their own, apart from committed references: GC never reclaims a staged fragment, and the post-restore pass never marks one, whatever state the upload is in. Both passes read each upload's staging entries, then its committed parts, and only then the committed objects, so a part commit or a publication that lands while they read leaves every chunk visible in at least one of the three. The upload records are read a page at a time — the list of uploads, then each upload's own records — never in one listing of a whole namespace. A staged record a pass cannot read at all stops it from reclaiming or marking anything until the record is repaired, and the post-restore pass names that record in its report; a staged record a pass can read but not trust holds only that chunk's fragments; and a store fault while reading staged records fails the pass. The post-restore pass protects the upload records already written when it reads them; it is run with writers stopped. The drain-status query reads these records too, and counts a staged fragment as held: a drain is reported finished only once no byte that can still become referenced is left on the server — neither one a committed object places there nor one an upload has staged there — because telling an operator a server is safe to wipe while a live upload's bytes sit on it is the same permanent loss as deleting them. That answer covers the records the query read; keeping an upload from staging a new byte onto a server after its drain was requested is a precondition on the upload's own staging write, which no writer carries yet because none exists. A staged record that query cannot read, or can read but not trust, blocks every drain the same way an unreadable or untrustworthy committed record does, and is named in the answer. The evacuation loop is the other side of that: it moves committed content only and never rewrites an upload's own records, so a server holding only staged bytes has nothing for it to move and waits instead for those uploads to finish, abort or be reaped. Scrub reads committed references and, of an upload's own records, its committed parts alone — never its in-flight staging entries, since checking a fragment needs the committed scheme a part record carries; it too reads the committed parts before the committed objects, so a chunk a publication hands over mid-pass is still checked instead of certified unread. Once a committed object names a chunk, scrub checks the chunk where that object places it, not where the upload's part record does: the part record stays until the upload's records are retired and is not updated when the repair loop moves a fragment, so the position it names may hold nothing, and checking it there would have scrub queue, every pass, a repair the repair loop finds nothing to do for and drains. A part record scrub can read but whose placement it cannot trust is named, and for a chunk no committed object names it stops scrub from reporting the store checked, since that chunk was not. The repair loop settles an obligation for a chunk a committed object names against that object alone, as it always has, whatever a leftover part record says. For a chunk no committed object names, it reads the staged classes first, so a publication landing mid-pass is seen in at least one of them. While the upload is still open, a chunk its committed part names is repaired like a committed one — its obligation drained as a duplicate finding if nothing is missing — by a move that strands nothing it writes. The pass rebuilds the missing fragment and chooses a destination in a free failure domain, on a server of its fleet that carries no drain or decommission record of any value; it marks the destination position before writing there, with a fresh mark stamped from the reconstruction clock whatever mark was there before; it authorizes the writes only while that mark is younger than the longest a mover may take between marking a position and authorizing the write into it, and sends all of one move's writes together, each with a deadline the mark's stamp fixes, which the D server refuses to accept at or after — so one slow write never uses up the time another has, and a chunk missing several fragments is repaired in one pass when every write lands in time; and it then adopts the fragment in one commit, conditioned on the upload's record, the part record, the destination's mark and the absence of a drain record on the destination, which repoints the part record, removes the destination's mark, marks the position it vacates and removes the obligation. If anything changed in between — the upload fenced by a complete, an abort or a reaper, the part record rewritten, a drain recorded, GC deciding to reclaim the mark — or the D server refused the write or could not confirm it landed in time, nothing is adopted: the part record is left as it was, the destination's mark stays over whatever was written, for GC to reclaim after its grace, and the obligation stays queued. A position whose mark GC is already reclaiming, or whose mark cannot be read, is never written, and rules out only that position, not its server; a vacated position whose mark cannot be read, or an upload record that cannot be read, withholds the repair before anything is written and is named for an operator. The pass keeps the obligation, and does not report the pass finished, while the chunk is named only by an in-flight staging entry, while its upload has left the open state — the repair is retried once the chunk is published — or while an upload record holds it with a placement that cannot be used. A destination mark a stopped move leaves with no fragment beneath it names the move that wrote it, so GC's sweep of such records leaves it in place, as it leaves every record that names its event. One case is bounded rather than prevented: if the published object is deleted or overwritten before the upload's records are retired, after the repair loop moved one of its fragments, the leftover part record again names the chunk with no committed object to overrule it, at a position that now holds nothing, so scrub queues the chunk and the repair loop keeps it, every pass, until the drain that retires the upload's records deletes the part record.

   Work too large for the batch that creates it — the records a multipart publication leaves behind, a rolled-back completion attempt's segments — is recorded as a **retirement obligation**: one small record installed in that same batch, which the custodian drains afterwards, a bounded batch at a time, as part of every repair-loop pass. A pass looks at a fixed number of obligations, reads a fixed number of pages and commits a fixed number of batches, whatever the size of the ledger. It resumes after the last obligation the previous pass looked at and returns to the start once it reaches the end, keeping where to resume in one small record of its own, as GC's walk does; an obligation the drain cannot work on still counts against the pass, so a run of them delays the rest by at most a lap and never blocks them. Each batch deletes the next records the obligation names and writes the obligation back with its progress — a cursor kept inside the obligation itself, the batch conditioned on the obligation's exact stored bytes, so two drainers can never both advance it — and the batch that deletes the last record deletes the obligation with it. An obligation comes in one of two modes, named in its key. The first owes records whose bytes something else still protects — the published parts' records, whose bytes the published object now names, and a rolled-back attempt's segments, whose bytes the upload's own parts still name — and its drain only deletes, never writing a grace record. An attempt's segments are found by reading its range, since the obligation names the attempt and not how many segments it wrote, and they count as done only when the store says no segment follows the batch — a page the store returns shorter than asked is never taken for the end — and a read of the whole range from its start finds none left. An obligation the drain cannot act on — one that does not decode, one whose progress would no longer fit the store's value ceiling, one whose recorded progress disagrees with what the range holds, one whose batch the store refused — is left exactly as it is and named to the operator, and the drain goes on to the next. A pass reports nothing left to do only when it read the whole ledger, from its start to its end, and found no obligation in it; one that resumed part-way, or left an obligation unfinished, says so and the next pass goes on. Every obligation is installed with room left for its cursor under the value ceiling, so one written by this build always fits. The cursor is a field an older build does not know: downgrading past it loses no data, since GC protects by an obligation's presence and never decodes one, but the older post-restore pass reports an obligation carrying a cursor as unreadable.

   The second mode owes **bytes** nothing will name once the obligation is gone — an aborted upload's parts and staged residue, the parts a completion left unnamed, a re-uploaded or losing part's chunks, a superseded or deleted generation's chunks or segments — and its drain **writes the grace record of every fragment position before it deletes the record that named it**, in an earlier commit, never the same one; a row whose bytes no record names goes with its last grace record. Each grace record names the obligation that wrote it, and GC leaves a fragment alone while that obligation is present, so the grace window of drained bytes **starts at the drain**: each batch is stamped with the repair loop's own clock, read for that batch once its obligation is in hand, never the pass's earlier reading, so an obligation installed while the pass ran gets grace records no older than itself. A record already naming this obligation is left as it is; one naming another event, or none, is replaced under a condition on its exact value; an absent one is written under a condition that it is still absent. A record GC has moved to *reclaiming* is never replaced, whatever it names: where no record the drain keeps names its position, GC destroys the fragment and deletes the record itself, and the drain writes a fresh one after, which GC's sweep of records with no fragment beneath them deletes once the obligation is gone and the late-write deadline has passed — as it does every grace record the drain wrote over a position with no fragment; where an upload part the drain still keeps names it, GC never moves (the upload's own protection outranks the record) and the drain does not either — the obligation is held, named to the operator as needing a human, and only an operator's repair moves it. A segmented generation's segments are read when the drain reaches them, so a fragment a repair moved before the supersede is marked where it now is. The drain checks every placement before it marks from it and holds an upload part whose placement is not one server per fragment, deleting nothing under it — unless the upload was aborted, when the part is retired by chunk id as described below; it holds an obligation whose record it was part-way through marking is gone when it returns, since nothing is left to name the rest of that record's positions; it waits on an ended upload's obligation while the upload still owns staged residue, which the upload's own teardown below empties first; and it deletes no part of an upload whose rolled-back attempt still has segments owed, so the post-restore check never reads an honest half-drained state as damage. Each batch reads and writes at most a fixed number of grace records and records, whatever the size of the obligation.

   A multipart upload that has ended — aborted, or completed — **leaves the store at a terminal delete**, in the same repair-loop pass, before the obligations are walked. The custodian walks the upload's own staging entries — the residue of a part whose write stopped before it committed — writing the grace record of every position an entry names, under the upload's own identity, and deleting the entry in a later commit; nothing refills that range once the upload has ended, so the entries left are the progress. An entry can name more positions than one batch reads (a wide erasure scheme, or a damaged placement), so the walk keeps how far it has got inside one entry in one small record of the custodian's own per upload, written in the batch whose grace records it counts under a condition on its exact value — and put only while the upload's record is unchanged, so a batch that lands after another drainer has ended the upload leaves none behind — and removed with that entry or, at the latest, with the upload. It names the first entry the last batch left that the walk can still work on — whatever it covered of it — and the next batch walks that entry first, so an entry held for the operator ahead of it never stalls it. A batch that writes no grace record and deletes no entry can only move that record: it is outside the pass's batch budget and ends the upload's turn for the pass, so uploads whose held entries keep moving it cannot starve the rest. Entries held for the operator stay in the range, so a second small record per upload says where the walk's next read starts: a batch that marks and deletes nothing and holds something moves it past the held entries at the head of what it read — leaving the first record on a held entry rather than moving it to the entry it has only read again, which the next batch reads first — and once nothing is left after it the walk is back at the start of the range and the record is deleted. Every entry is therefore read once a lap however many are held ahead of it, and each held entry is named to the operator again every lap. That record is a position, never evidence — what an entry's deletion needs does not change with it, and one that names nothing of the upload's range is named to the operator and read as the start. It is written in a commit of its own, outside the pass's batch budget so that uploads with held entries cannot starve the rest, at most twice per upload a pass, put only while the upload's record is unchanged, and removed at the latest with the upload. Once a pass finds the range empty and no obligation of the upload left, one batch, conditioned on the upload's record exactly as read, deletes the record and the slots its parts reserved, deletes the reservation of its segment group unless a published object adopted the group, and lowers the admission count by one: of two drainers that race to it, one commits and the other's batch is refused, so the count goes down exactly once and an admission slot is released once. A **completed** upload's record is the tombstone that answers a retried completion with the published result, so it is kept, and its admission slot with it, until its tombstone window has passed; nothing measures that window yet, so the deployed custodian keeps every completed upload's record for now. For an **aborted** upload only, a record whose placement cannot be trusted — a part or a staging entry whose placement is not one server per fragment, or a staging entry that will not decode under a key that still names its chunk — is retired **by chunk id**: every fragment of that chunk that the D servers' own listings show gets a grace record, and for a staging entry that decodes so does every position it names, before the record goes. This runs only on a pass that sees every server the operator configured, the condition GC already runs under, since a listing that misses a server would leave that server's fragments with neither record nor grace record; on any other pass the record is held and named to the operator, and nothing is lost while it waits. The positions a record names itself are a fixed order, so the drain resumes inside them from its cursor across as many batches as they need. A listing is no such order — a fragment that drops out of it moves every later one — so a batch that reaches a chunk's listed fragments reads all of them, and progress is counted a whole chunk at a time; a chunk listed with more fragments than one batch reads is held and named to the operator as needing a human. A batch lists the fleet at most once, so a pass lists it at most once per batch it commits, plus once per aborted upload whose damaged record is held after its listing. One gap is stated rather than hidden: a write the aborted upload had authorized that lands after the listing, at a position the damaged record does not name, has neither record nor grace record, and GC keeps it — kept for good, never lost, never reclaimed without an operator. A part record that will not decode names no chunk in its key, so it is held for a human, and the upload stays until one acts. A grace record the walk wrote over a position whose write never landed stays as well, since that write may still land there.

   A multipart upload whose client went silent — never aborted, never completed — is ended by the **multipart reaper** (proposal 0016 decision 6), which runs in the same repair-loop pass, after reconstruction and before the terminal deletes and the obligation walk, so an upload it ends is drained in the same pass. A reconstruction failure does not skip them: the pass still reports it, but only after the reaper and the drain have had their turn, so a fault reading the repair queue cannot keep abandoned uploads holding their admission slots. It first compares the budget profile the admission record stores with its own and, if they differ or the record will not decode, stops before reading any upload and names the mismatch for an operator — and the terminal deletes and the obligation walk do not run in that pass either, since they build the staged references that profile sizes, so no upload's records change in that pass. It reads the admission record once more as the last thing it does, just before those legs run, so a record installed or replaced under another profile while it worked — a first upload created by a differently sized gateway — stops them the same way. With no admission record at all nothing was ever admitted, so it judges no upload. If the record is still missing at its last read while an upload is listed — or the listing cannot be read — the record is lost and the profile those uploads were admitted under is unknown, so the pass is refused as for a mismatch, and the terminal deletes and the obligation walk do not run either. A record that was there at the first read and is gone at the last is lost in the same way — nothing deletes it — and refuses the pass the same way, whatever the pass did before that read. A refusal at the first read says that the reaper refused before acting; one at the last read of a pass that had judged says how many uploads it had already ended — they stay ended, under the profile the first read matched — and the pass's counts are reported either way, as they are when that last read fails. A first upload created under its own profile while the pass works is left for the next pass, and that pass reports that it did not finish rather than that nothing is left. It lists the uploads in key order, at most a fixed number per pass, and keeps where it stopped in a position of its own, `custodian:reaper-cursor`, so the next pass goes on from there and every upload is judged once a lap (a stored position that is not an upload key a backend accepts is named and replaced by the head, never handed to the store). When that number runs out it reads one entry further, judging none, so a listing that ends exactly there is known to have ended. A read of the listing the store cannot answer — a page of it, or that one entry — holds the rest of the listing for that pass, named for an operator, and sends the next pass back to the head rather than to the read that failed, so a fault that lasts never keeps the uploads listed before it from being judged again. The position also records whether the lap so far is clean — nothing ended, contended or held since its head — so the pass that finishes a clean lap reports that nothing is left, and one that finishes any other lap reports that it did not finish, and a longer listing still reaches the first report once a whole lap finds nothing to do; the admission count does not bound the listing, since a lowered limit or uploads created and deleted between two pages can list more uploads than the count, and neither is damage. It judges only an **open** one stamped under the clock it reads. An upload stamped under another clock is named for an operator and never judged; while it is open only an operator can end it, so it is held, and once it has ended its teardown runs as any other's, since none of it reads a timestamp. An upload whose creation or newest progress is stamped later than the reaper's own clock by more than the clock-skew budget is held too, rather than kept for as long as the stamp stays ahead. An open upload is ended when it is **idle** — its newest progress (its creation, its newest committed part, its newest in-flight slot reservation) is older than the idle window and no slot or staging lease of it is still live — or when it is **over age**, older than the residency ceiling however live it is. It reads the slot range before the part summaries, so a part committing between the two reads is seen in one or both, never neither. An upload whose records it cannot read or decode — a part summary under a key that names no part included — is held and named for an operator, and the pass goes on to the next and to the terminal deletes and the obligation walk. Ending an upload is the one commit a client abort also makes — the upload moved to aborting under a condition on its exact record, with the obligation owing everything it staged — and the idle commit also pins every slot of the upload as read, present or absent, so a renewal or release of a slot it read, or a reservation still standing when the commit lands, makes the commit fail and the upload is judged again next pass; the over-age commit pins nothing. A commit that fails because the upload's teardown obligation already exists beside its unchanged record is damage rather than contention, since no writer leaves that state: the upload is held and named. A commit whose outcome the store could not report is neither a success nor a failure: the upload may already have been ended, and the drain of that same pass then tears it down, so it is never reported as left in place and never counted as ended. It is named for an operator and counted on its own, the pass reports that it could not account for everything, the commit is not sent again, and the next pass reads which way it went. One gap is stated rather than hidden: a request that reserves a slot the reaper read free and commits its part, both between the reads and the idle commit, leaves every slot as the reaper read it, so the commit lands and that upload is ended together with the part it has just committed. Closing that needs a change to the upload protocol (proposal 0016) that this release does not make; it is a known gap, and the follow-up that closes it must land before uploads are created in production. Each commit is measured against the batch budgets before it is sent and never split. An operator can run exactly one such pass and exit with `wyrd custodian --reap-abandoned-uploads`: it needs no `--endpoints`, reads and writes metadata only, and drains what it ended record by record, holding for a whole-fleet pass anything that could only be retired by listing the fleet; it exits non-zero when anything was held, a commit's outcome is unknown or the profile check refused, so an open upload under another clock keeps it failing until an operator ends that upload. It is refused before it opens the store when given a flag that selects work it does not run — `--endpoints`, `--ids`, `--failure-domains` or `--gc-expired-pending` — rather than ignoring the flag, and when its `--data-dir` holds no local metadata store — no file there, or an empty one — which it never creates: a store made on the spot would be reported as holding nothing to reap. Its last line names the store it ran on: the local file, or the TiKV PD endpoints or the FoundationDB cluster file it connected with. The reaper runs on every startup shape of the ordinary role, not only on a healthy fleet. With a fleet it rides each interval's repair-loop pass over whatever part of the fleet is reachable, so a server down at startup or unreachable this pass defers garbage collection but not the reaper; the drain after it still waits for a pass that sees the whole fleet before it retires anything by listing the fleet. With no `--endpoints` the role has nothing to reconstruct but does not exit: it runs the reaper alone, record by record, through the same interval loop as the fleet role, until it is stopped. Like the fleet role it waits `--interval-secs` between two passes; with no `--endpoints` an interval of 0 is refused, since it would run them back to back, while the role given `--endpoints` takes 0 as it always has. Both loops register Ctrl-C before their first pass, so a stop takes effect between two passes, never during one, the first pass included: the pass in hand finishes and the role exits 0. A stop that is already there when the interval runs out wins over the interval, so no further pass starts. A pass is bounded by what it may do — the reaper's and the drain's per-pass budgets — and, on TiKV and FoundationDB, by each store call's own operation deadline; there is no deadline on a pass as a whole, so a slow pass is never cut off and repeated from the start. Without a fleet the role reaps a store that is already there and creates none: on redb a data directory that holds no store is refused, since a store made at a mistyped path would be reaped, empty, while the cluster's went unreaped. On redb the role with no `--endpoints` also holds the store's exclusive lock for as long as it runs, as the fleet role does, so no other `wyrd` process can open that store until it stops. It is also refused with `--gc-expired-pending`, `--ids` or `--failure-domains`, which only a fleet uses. When `--endpoints` are given and none of them is reachable at startup, the role runs exactly one reaper pass under the leadership it already holds and then fails as before, with a non-zero exit and the same diagnostic, so a supervisor restarts it. That pass does not wait for a stop: a Ctrl-C during it ends the process at once, as it ends a one-shot, and what the pass had committed stays for the next start's pass to go on from. The role is not kept up on the empty fleet, because it never dials a server again after startup. The restore one-shot, `--reconcile-after-restore`, runs no such pass: on a just-restored store the restore pass is the first to act, and a restore run that fails on an empty fleet leaves the store as it found it.

   An upload the reaper will not judge — one stamped under a clock it does not read — is ended by an **operator abort**: `wyrd mpu abort --upload-id ID [--data-dir DIR] [--metadata-backend B]` (proposal 0016's operator exit, FU-6). It names exactly one upload, by its id — a second `--upload-id`, a pattern or a wildcard is refused, and so is any flag it does not take, a clock source among them, since it judges no clock — and it acts on the store the cluster wrote, never creating one. Its command line is read strictly, before the store is opened: each flag at most once and with a value, a value that is empty or spelled as a flag (`--data-dir --bogus`) refused rather than taken, and `--data-dir` refused on a networked backend, which takes its address from the environment and would ignore it. An **open** upload is moved to aborting with the obligation owing everything it staged, the same commit a client abort makes. An upload **completing** — a publication fenced and stopped — is moved to aborting with that obligation and a second one owing the segment records its attempt wrote, the range of that attempt alone and never the upload's later or earlier attempts, the same commit the post-restore pass makes for such an upload. Each is one commit, conditioned on the upload's exact record and on the obligations being absent, so no state has the upload aborting with something it holds that nothing will reclaim. The abort deletes nothing, writes no mark and leaves the admission count alone: the teardown is the drain's, which reads no clock, so the operator runs `wyrd custodian --reap-abandoned-uploads` after it, or leaves it to the deployed custodian's next pass. The abort prints that one-shot spelled for the store it acted on, so the line can be run as printed from any shell: the backend by name; for redb the directory, made absolute against the directory the abort ran in; for a networked backend each environment variable its open reads how to reach the store from, with the value it resolved to, as an assignment scoped to the command — for FoundationDB the cluster file and, when one is set, the multi-version client's external-client directory, each made absolute the same way; each value quoted for a shell. A path the line would carry that resolves to no UTF-8 spelling is refused before the store is opened, since no printed line could name it. The abort's `[store: …]` label names the same absolute path. A pass reports on the whole store, so any other upload it holds makes every pass report `BLOCKED`, with exit 1, while this upload's teardown goes on; the abort therefore prints a stop condition for this upload alone: run the one-shot until the same abort, which it also prints, answers that the upload is absent. A pass that holds this upload itself, such as one held for a partial fleet, will hold it again; the abort says to stop the metadata-only one-shot then and run the custodian over the same store with the whole fleet (`--endpoints`, `--ids`, `--failure-domains`). An upload already aborting is left as it is and the abort exits 0; a **completed** upload is refused, since abort does not apply to a terminal session, and so is an upload with no record, each with exit 1 and a message naming what it found. A commit that loses to a change of the record is answered from what the record now holds, and a commit whose outcome the store could not report is settled by reading the record again, claiming no more than that read shows: found moved to aborting as that commit moves it, the abort reports the upload aborting, by its commit or by a rival one that writes the same record, exit 0; found gone, it reports the upload possibly fenced and already torn down, never that nothing was written, exit 1; found unchanged, it tries again. It makes a bounded number of commits, and if it stops with one of them possibly still landing it exits 1 saying so, so a re-run reads which way it went. This verb is an interim surface on the development CLI, granted until the management plane of proposal 0008 exists: its authority is host access to the metadata store, with no listener and no authentication path of its own, and it moves onto the management API when that lands, with the same semantics and the same records.
3. **Propagate across zones (L3).** If the object had replicas, the deletion propagates through the replica catalog: each holding zone drops its catalog record and its GC reclaims the local fragments. Until propagation completes, a *stale-tolerant* read in a lagging zone may still see the old object, bounded by replication lag (section 8.1); consistency-sensitive reads route to the home zone and never do.
4. **Prove it (audit + crypto-erase).** The deletion is recorded in the append-only audit/event log — the operator's compliance and GDPR-deletion story (section 8.3). Where per-tenant envelope encryption is enabled, dropping the object/tenant key crypto-shreds the data immediately, making it unrecoverable independent of when GC runs (section 8.5).
